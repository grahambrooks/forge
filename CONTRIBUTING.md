# Contributing to Forge

Thanks for taking an interest. Forge is a single Rust crate with a large
surface area — a DSL parser, a layout engine per view type, an SVG renderer, a
static site generator, an LSP server, and a set of codebase scanners. This guide
covers how to build it, what the quality gate is, and how changes get released.

[DESIGN.md](./DESIGN.md) is the source of truth for design decisions. Read the
relevant section before changing behaviour; if your change contradicts it,
update `DESIGN.md` in the same PR.

## Getting set up

You need a stable Rust toolchain and a C toolchain — the `symgraph` dependency
builds tree-sitter grammars from source (Xcode Command Line Tools on macOS,
`build-essential` on Debian/Ubuntu).

```bash
git clone https://github.com/grahambrooks/forge.git
cd forge
make build
make run     # renders every view from the bundled example
```

Docker is optional, and only needed for the integration and install test
suites.

## Repo layout

There is **no `Cargo.toml` at the repo root**. The crate lives in `forge/`
(package `forge-dsl`, binary `forge`), so bare `cargo` commands must run from
`forge/`. The `make` targets handle this for you — prefer them.

```
DESIGN.md              Design spec — the source of truth
CONTRIBUTING.md        This file
Makefile               Every workflow: build, test, lint, eval, release
Formula/forge.rb       Homebrew formula (generated by the release workflow)
docs/                  User guide, reference, and roadmap
forge/src/             The crate
  main.rs              CLI entry point (clap subcommands)
  model.rs             Semantic model — elements, relationships, views
  parser/              Hand-written recursive descent parser
  layout/              Content-aware layout, one module per view type
  render/              SVG rendering
  analyze/             Codebase scanners (code, ci, docker, git, k8s, ...)
  generate/            Static site generator
  check/               Architectural lint rules
  mcp/, lsp.rs         AI-agent and editor integration
integrations/          MkDocs plugin, Backstage example, Claude plugin
tests/integration/     Docker-based end-to-end and install tests
eval/                  Scanner accuracy evaluation harness
```

Several modules are mid-migration from a single fat file to a directory module
(you will see both `parser.rs` and `parser/`). New code goes in the directory
module. See the Modularity Roadmap section of [CLAUDE.md](./CLAUDE.md) for the
order of that work.

## The pre-commit gate

**Run `make pre-commit` from the repo root before every commit.** It runs
exactly what CI runs — `cargo fmt --check`, `cargo clippy -D warnings`, and the
full test suite — and prints `All pre-commit checks passed.` when clean.

```bash
make pre-commit
```

If it fails:

1. Formatting failures: run `make fmt`, then re-run the gate.
2. Clippy or test failures: fix the underlying problem.

Do not silence a failure with `#[allow(...)]` or bypass the gate with
`--no-verify`. Skipping this is how formatting drift and clippy regressions
land on `main` and break the build for everyone.

## Running things locally

`make help` lists every target grouped by section. The common ones:

| Command | What it does |
|---------|--------------|
| `make build` / `make release` | Build the binary (debug / optimized) |
| `make test` | Unit and integration tests |
| `make lint` / `make fmt` | Clippy with warnings-as-errors / rustfmt |
| `make pre-commit` | The full CI-equivalent gate |
| `make run` | Render every view from the bundled example |
| `make check` | Run `forge check` against the bundled example |
| `make integration-test` | End-to-end tests in Docker |
| `make install-test` | Install tests across Debian, Ubuntu, Fedora, Alpine, Homebrew, cargo |
| `make publish-check` | Dry-run the crates.io package step |

To exercise the CLI directly while developing:

```bash
cd forge
cargo run -- build --source examples/payments.forge --out output
cargo run -- check --source examples/payments.forge
cargo run -- serve --source examples/payments.forge --port 4000
```

`forge/examples/payments.forge` is the reference model — 30 elements across 11
views. Most integration tests parse it, so it is the fastest way to see the
effect of a rendering or layout change.

## Tests

Unit tests live in a `#[cfg(test)] mod tests` block at the bottom of the module
they cover. Integration-style tests that need Docker live in
`tests/integration/`.

**Tests must be hermetic.** Build fixtures in a temp directory; never read the
surrounding checkout, the developer's home directory, or the network. This bites
in a specific way: a test that inspected the ambient git repo for branches passed
on every laptop and failed on every PR, because CI checks out a detached HEAD
with no local branches. If you need a git repo, a `.forge` file, or a
`CODEOWNERS` file, construct it under `tempfile::tempdir()` — see
`fixture_repo` in `forge/src/analyze/git.rs` for the pattern.

When adding a scanner or lint rule, add a fixture-backed test proving it fires
on a positive case *and* stays quiet on a negative one. Silent false positives
are the main failure mode for both.

## Coding conventions

- **Formatting**: `rustfmt` defaults, enforced by the gate. No custom config.
- **Clippy**: warnings are errors. Fix the cause rather than allowing the lint.
- **SVG output**: every element gets a semantic CSS class with a `forge-`
  prefix, and output SVGs stay self-contained — no external references.
- **Raw strings**: use `r##"..."##` for strings containing `"#`, which is
  common in SVG colour values.
- **Comments**: explain why, not what. Match the density of the surrounding
  code.

## Pull requests

`main` is the default branch and is not protected, which makes the convention
more important, not less:

1. Branch off `main` — do not commit to it directly.
2. Keep the change focused. Unrelated fixes belong in their own PR.
3. Run `make pre-commit` and make sure it passes.
4. Open a PR describing what changed and why. Link the `DESIGN.md` section or
   `docs/roadmap.md` item if there is one.
5. Wait for CI. The workflow runs Test, Lint, Build Example, Integration Tests,
   and a six-way Install matrix.

Commit messages follow Conventional Commits (`fix(analyze): ...`,
`chore(deps): ...`) — the dependency bots depend on this, and it keeps the
release notes readable.

Dependency PRs are opened by Renovate and merged automatically once CI is
green, so you will see bot traffic on `main`. If your branch conflicts with one,
merge `main` into your branch rather than force-pushing a rebase.

## Releases

Releases are CalVer (`vYYYY.MM.DD`) and are cut from `main`:

```bash
make release-github
```

That target runs the pre-commit gate, stamps the date-based version into
`forge/Cargo.toml`, verifies the built binary reports that version, commits,
tags, and pushes. Pushing the tag triggers
[`.github/workflows/release.yml`](.github/workflows/release.yml), which:

1. Verifies the tag matches `forge/Cargo.toml`, and fails the release if not.
2. Creates the GitHub release.
3. Builds and uploads tarballs for `x86_64-unknown-linux-gnu`,
   `aarch64-unknown-linux-gnu`, and `aarch64-apple-darwin`. Intel Macs build
   from source instead.
4. Publishes `forge-dsl` to crates.io. This step is skipped if the version is
   already published, so re-running a release is safe.
5. Regenerates `Formula/forge.rb` from the published checksums and commits it
   back to `main`.

Publishing needs a `CARGO_REGISTRY_TOKEN` repository secret with
publish-update scope for `forge-dsl`. `Formula/forge.rb` is generated by
`scripts/render-formula.py` — edit the template there, not the formula, or your
change is overwritten by the next release.
